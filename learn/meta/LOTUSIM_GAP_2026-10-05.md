# 读 LOTUSim 源码：我们和它的差距，补我们的还是改它的动力学（2026-10-05）

用户的问题（原话）："好像lotussim是开源的，能不能下载下来看我们和他们还有什么差距？把我们的再加上差的部分或者用他们的改一个动力学？"

**做法：**
- 经用户确认，浅克隆了三个仓库到 `C:\Users\Administrator\Documents\ext_sims\`，只读、没有编译和运行：
  - LOTUSim 主仓库（提交 1f7d34f）；
  - 物理引擎 lxdyn（xdyn 的海军集团版本）；
  - Unity 渲染模块。
- 四路分别读：LOTUSim 主体、lxdyn 物理（与我们的高保真船逐项对照）、Unity 渲染、我们自己的系统和接入方案。
- 综合后两路逐条反驳核对，45 条里 40 条确认、5 条修正，修正已并入下文。

## 结论

- **LOTUSim 自己不算船的动力学。** 它是 Gazebo 加 ROS 2 的外壳：Gazebo 自带的刚体物理在主要场景里是关掉的。船的位置姿态有三种来源：
  - 每一步把状态通过网络连接发给外部的 xdyn 程序算；
  - 一个按航点走的运动学跟随器；
  - 外部直接设定。
- **对我们这条滑行喷泵艇，xdyn 缺了所有关键的东西：** 滑行升力、拍水冲击、随浸没变化的附加质量、喷泵。
  - 它只有两处比我们强：任意姿态下按船体网格精确算浮力（横摇和升沉、纵摇耦合起来），以及完整的大角度姿态运动学。
- **它领先的是"产品层"：** ROS 2 接口、多船、传感器、地理坐标、场景文件、网页界面、Unity 画面。但其中不少还不成熟（见下文）。
- **我们领先的是：** 物理逼真度；画面里的浪就是物理里的浪；结果逐位可重复；原生 Windows。

## 逐项对照

| 方面 | 我们 | LOTUSim（xdyn） |
|---|---|---|
| 滑行升力 | 有（48 个切片的切片理论） | 没有 |
| 拍水冲击 | 有（入水动量项，已知低估约 1.5–2.5 倍） | 没有 |
| 附加质量 | 每步按浸没重算 | 常数矩阵 |
| 浮力 | 按切片对当地波面；横摇不进浸没 | 更好：任意姿态精确裁切船体网格，六个方向耦合 |
| 波浪压力力 | 当地浸没浮力加波面斜率项 | 在湿表面上积分非线性压力 |
| 绕射、辐射 | 相对运动的切片项，无记忆 | 线性数据表（要另做面元计算）；在 LOTUSim 里每步只发一个状态，记忆项实际被截断 |
| 阻力 | 湿表面摩擦加切片压差阻力 | 阻力表或排水型船的经验公式 |
| 横荡、艏摇、横摇 | 占位级的简化 | 排水型船的操纵模型 |
| 喷泵 | 有：延迟、滞后、出水吸空、喷嘴转向 | 没有（只有螺旋桨、舵、翼型） |
| 风、流 | 滑行艇模型里没有 | 有风；流的处理看起来重复算了一次（自由漂浮的船会以约两倍流速漂走） |
| 波浪 | 线性分量和，固定种子 | 线性分量和；可以在配置文件里直接列分量，所以能喂入我们的海浪；有限水深分支的判断写反了 |
| 传感器 | 没有（控制器读真实状态） | 船舶自动识别系统、惯性测量、由激光雷达生成的雷达、压力、Gazebo 的激光雷达、定位、磁罗经；但接 xdyn 时惯性测量实际上只有姿态；相机只在 Unity 里 |
| ROS 2 | 没有 | 完整，但位姿不带速度，没有统一时钟，指令是整段 JSON 字符串 |
| 多船 | 每个任务一条 | 任意多条，彼此没有物理相互作用 |
| 场景 | 写在代码和命令行参数里 | YAML 场景文件，但不读环境和海况 |
| 画面 | 网页实时和 Blender 照片级，浪和姿态与仿真一致 | Unity 实时，但水面与物理不同步；能画我们这种分量海浪的分支没接进项目；它自己的位姿发送端和 Unity 接收端的端口、字段对不上 |
| 可重复性 | 逐位相同 | xdyn 本身确定；但桥接层不确定：指令按真实时间到达，超过 5 秒没回复就丢一步，有一处等待信号的竞争 |
| 平台 | 原生 Windows | 主体要 Linux 或 Windows 上的 WSL2 虚拟机（建议给 16 GB 内存）；Unity 画面能原生在 Windows 上跑 |
| 小艇模型 | 我们这条船，已建模 | 没有能用的小艇：一个是占位立方体；另一个有基本受力，但缺船体网格文件 |

**对早先网上调研结论的修正：**
- 我们的波浪分量可以直接写进 xdyn 的配置，不需要网络接口。
- 结果不可重复的原因不是"故意打乱顺序"（打乱的只是互相独立的各船的更新顺序，无害），而是桥接层的计时问题。
- "只能用 WSL2"只针对 Gazebo 和 ROS 2 主体；Unity 画面和 lxdyn 本身可以在 Windows 上跑。
- 带学习模型的控制器单独运行时每步约 2.3 秒，比实时慢约 10 倍。它不会撞上 5 秒的物理回复超时，因为控制器走的是 ROS 2 消息，不在物理回复里；但要接进去，需要一个外部"暂停—走一步"的调度。

## 三条路线（一个熟悉我们仓库的人，工作量为估计）

**甲：把缺的产品层补到我们这边（原生 Windows）。**
- 核心约 1.5 周：
  - 一个仿真服务：多条船共用一片海，可以一步步走（锁步）也可以按真实时间走，结果和现在的评估逐位一致；
  - 场景文件，键名沿用 LOTUSim 的写法以便兼容；
  - 统一的记录；
  - 测试。
- 需要时再加约 2.5 周：
  - 传感器模型（惯性测量、定位、航向、航速，带噪声和延迟；以及由其他船真实状态生成的识别和雷达目标）；
  - 一个单独进程的 ROS 2 桥。
- 好处：物理不动，结果可重复，演示用现有的画面就够。
- 缺点：没有相机、激光雷达图像和港口场景。

**乙一：用 LOTUSim，把动力学换成我们的。**
- 写一个小服务，冒充 xdyn 的网络协议，背后是我们的高保真船。LOTUSim 的代码一行不用改。
- 约 2–3 周，包括坐标系转换测试、模型文件、装 Linux 环境，以及给慢控制器用的外部暂停调度。
- 好处：进入它的 ROS 2 生态，有它的传感器、地理坐标、网页界面和 Unity 场景（但水面不是我们的海）。
- 风险：
  - 这台 16 GB 机器跑 WSL2 吃紧；
  - 结果不可重复，偶尔卡 5 秒；
  - 位姿每秒只有 5–10 次，不带速度；
  - 没有波浪画面；
  - 桥接层的姿态和时间错误 9 月 24 日才修好。

**乙二：把我们的力移植进 lxdyn。** 不建议。
- xdyn 只剩积分的作用；
- 喷泵的内部状态放不进它无状态的力模型；
- 要整个重新验证；
- 约 3–6 周，风险高，没有收益。

**丙：我们的仿真仍是物理和时钟，只把位姿送给 Unity 画面或 ROS 2。**
- 要改 Unity 工程里时间和坐标的处理，还要做一个我们的船的三维模型。
- 要让水面等于我们的海，还得写着色器（1–3 周）。
- 只是布景，不影响结果。

## 建议

1. **现在做甲的核心**（约 1.5 周）：仿真服务、场景文件、记录和测试。团队确实要 ROS 2 时再加传感器和 ROS 2 桥。
2. **接口按 LOTUSim 兼容的格式设计**（东北天坐标的位姿加地理点、JSON 指令）。这样以后有人要把船放进 LOTUSim，乙一只是一层薄适配，几天就能接上，最好放在 Linux 机器上。它只用于接口演示，不用于评估。
3. **不做乙二**，也不拿 LOTUSim 或 xdyn 的数据训练误差模型。
4. **物理上只借一个思路：** 横倾时各切片对当地波面裁切，让横摇和升沉、纵摇耦合。只有在横摇、转弯横倾或倾覆变得重要时才做，先推导，再重新验证。
5. **Unity 画面（丙）作为可选布景**，要 Unity 编辑器的工作，而且水面不是我们的海，除非另写着色器。
