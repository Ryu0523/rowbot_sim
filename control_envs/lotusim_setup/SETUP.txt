LOTUSim + Gymnasium setup
=========================

Purpose
-------
Run LOTUSim (Naval Group's open-source 3-D maritime simulator: Gazebo Harmonic +
ROS 2 Jazzy, with the xdyn physics server for vessel dynamics) and drive a
vessel in it from Python through a Gymnasium environment, so that two people
can use the same 3-D environment for control experiments.

What you get
------------
  control_envs/lotusim_env.py        the Gymnasium environment (LotusimEnv) and the
                                     ROS 2 link to LOTUSim (LotusimLink); a FakeLink
                                     lets you test the env without ROS on any machine
  control_envs/lotusim_gym_demo.py   spawns a vessel, drives it with a P controller,
                                     prints speed/heading, deletes it
  control_envs/lotusim_setup/
      SETUP.txt                      this file
      wslconfig.txt                  WSL settings for the Windows host
      configuration.nix.snippet      NixOS settings (binary caches, GPU, git)
      nixos_setup.sh                 one-time setup inside NixOS-WSL
      flake.nix                      Python dev shell: rclpy + lotusim_msgs + gymnasium
      run_sim.sh                     starts xdyn + LOTUSim (headless or --gui)
      run_gym_demo.sh                runs the demo inside the dev shell

Two routes
----------
  A. Docker (no Nix, headless, identical on every OS): see docker/DOCKER.txt.
     Smallest install for teammates; no 3-D window.
  B. NixOS-WSL (this file): full install with the Gazebo window and the web UI.
Both expose the same ROS 2 interface and use the same Python environment and demo.

How LOTUSim is installed
------------------------
LOTUSim is distributed through the Nix package manager. Nothing is compiled on
your machine as long as the two binary caches (ros.cachix.org and
naval-group.cachix.org) are trusted; otherwise Nix silently builds ROS 2 and
Gazebo from source for about an hour. On Windows, Nix runs inside NixOS-WSL
(a NixOS system under WSL2). On Ubuntu/macOS you install Nix directly.

Hardware notes (this machine): 16 GB RAM, 20 logical cores, Windows 11 Pro.
The WSL memory cap is set to 8 GB in .wslconfig; Gazebo + xdyn + ROS fit in it.
The Gazebo window needs a GPU driver bridge (configured below); headless runs
and the browser UI do not.


1. Windows host (one time, needs an administrator PowerShell)
-------------------------------------------------------------
1.1  Enable the WSL features. Already done on this machine on 2026-10-15 with
         Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Windows-Subsystem-Linux -All -NoRestart
         Enable-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform -All -NoRestart
     A RESTART IS REQUIRED before WSL works. (On a fresh machine the single
     command  wsl --install --no-distribution  does the same and may also need
     a restart.)

1.2  After the restart, install the WSL runtime:
         wsl --install --no-distribution
     If that command fails with "Windows Subsystem for Linux is not installed",
     the Microsoft Store is probably unreachable. Fallback: download the MSI
     installer (wsl.x64.msi) from https://github.com/microsoft/WSL/releases/latest
     and run it, then  wsl --version  should print a version (2.4.4 or later).

1.3  WSL settings. Copy  control_envs/lotusim_setup/wslconfig.txt  to
         %USERPROFILE%\.wslconfig          (file name is literally ".wslconfig")
     Already done on this machine. Contents:
         [wsl2]
         networkingMode=mirrored          ROS 2 discovery works; localhost is shared
         memory=8GB                       raise on a machine with more RAM
         swap=8GB

1.4  Install NixOS-WSL. The image is already downloaded and checksum-verified:
         C:\Users\Administrator\Documents\ext_sims\nixos_wsl\nixos.wsl   (578 MB, release 2605.7.2)
     Install it (WSL 2.4.4 or later):
         wsl --install --from-file C:\Users\Administrator\Documents\ext_sims\nixos_wsl\nixos.wsl
     Older WSL:
         wsl --import NixOS $env:USERPROFILE\NixOS C:\Users\Administrator\Documents\ext_sims\nixos_wsl\nixos.wsl --version 2
     Then:
         wsl -s NixOS          (optional: make it the default distribution)
         wsl -d NixOS          (opens a NixOS shell; the first start takes a minute)

     Another teammate downloads the same file from
         https://github.com/nix-community/NixOS-WSL/releases/latest   (nixos.wsl)
     and checks  sha256sum nixos.wsl  against nixos.wsl.sha256.


2. Inside NixOS-WSL (one time)
------------------------------
Your Windows drive is visible as /mnt/c. Run the setup script:

    bash /mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup/nixos_setup.sh

It (1) appends configuration.nix.snippet to /etc/nixos/configuration.nix,
(2) runs  sudo nixos-rebuild switch, (3) installs the lotusim and lotusim-ui
commands, (4) installs the xdyn physics server (xdyn-for-cs), (5) seeds
LOTUSim's state directory (~/.local/share/lotusim with models/, scenarios/,
worlds/). First run: a few minutes, mostly downloads (about 3 GB).

Then, in PowerShell:   wsl --shutdown      and reopen with   wsl -d NixOS

Manual equivalent (what the script does), from the LOTUSim README:
    sudo nano /etc/nixos/configuration.nix      -> paste configuration.nix.snippet inside { ... }
    sudo nixos-rebuild switch
    nix profile add github:naval-group/LOTUSim github:naval-group/LOTUSim#ui
    nix profile add github:naval-group/lxdyn


3. Run the simulation
---------------------
    lotusim --help              lists the worlds (lotusim.world is the default)
    lotusim run                 headless server (ROS 2 topics only)
    lotusim run --gui           Gazebo window; needs the GPU bridge from step 2
                                (hardware.graphics.enable + wsl.useWindowsDriver);
                                if no window opens, see Troubleshooting
    lotusim-ui                  web UI, open http://localhost:8080 in the Windows browser

Vessels with dynamics are computed by xdyn, a separate server LOTUSim talks to
over a websocket. For surface vessels start it on port 12345 before spawning:

    xdyn-for-cs ~/.local/share/lotusim/models/dtmb_hull/dtmb-xdyn-faster.yml --address 127.0.0.1 --port 12345 --dt 0.1

run_sim.sh does both (xdyn in the background, then lotusim run):

    bash /mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup/run_sim.sh          # headless
    bash /mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup/run_sim.sh --gui    # with window

Underwater vessels use a second xdyn on port 12346 (see LOTUSim's
examples/python-scripts/README.md); the demo below only needs the surface one.


4. What LOTUSim exposes (ROS 2, namespace /lotusim)
---------------------------------------------------
    /lotusim/poses              VesselPositionArray: name, pose (x,y,z, quaternion,
                                front-left-up), geo_point (lat, lon, alt); 10 Hz
    /lotusim/vessel_cmd_array   VesselCmdArray: per vessel a JSON command string,
                                e.g. {"PSPropRudd(rpm)": 15.0, "PSPropRudd(P/D)": 0.79,
                                      "PSPropRudd(beta)": -0.1, ...}   (SI: rad/s, -, rad)
                                keys are "<controlled force name>(<quantity>)" from the
                                vessel's xdyn YAML; the DTMB hull has PSPropRudd and
                                SBPropRudd (port/starboard propeller+rudder; rpm in
                                rad/s, beta in RADIANS -- measured, see section 7)
    /lotusim/mas_cmd            action: CREATE (spawn a model), DELETE, MOVE (teleport)
                                The CREATE goal carries a <lotus_param> XML string that
                                says how the vessel is driven (xdyn websocket URI,
                                thruster names, Surface/Underwater) - see
                                surface_xdyn_param() in lotusim_env.py
Vessel names are assigned by LOTUSim (model_name_<index>); the CREATE result
returns the actual name and LotusimLink.spawn() uses it.

Models shipped with LOTUSim (assets/models): bluerov2_heavy (underwater, xdyn),
lrauv (underwater, xdyn), dtmb_hull (surface, xdyn, twin propeller+rudder),
wamv (surface model, its xdyn YAML has no controllable thrusters), fremm,
commando, pha (static ships), x500 (aerial drone), plus landscape/seabed/mine.
Our own hull is not in LOTUSim; adding a vessel means writing an xdyn YAML
(hull mesh, hydrodynamics, controlled forces) and a model folder.


5. Gymnasium environment
------------------------
The env lives in control_envs/lotusim_env.py:

    LotusimLink(vessel_name)   ROS 2 node: subscribes /lotusim/poses, publishes
                               /lotusim/vessel_cmd_array, calls /lotusim/mas_cmd
                               (spawn / move / delete)
    LotusimEnv(link, dt, episode_s, target_speed, target_heading, cmd_fn)
        observation: [speed (m/s, from two poses), yaw rate, sin(err), cos(err)]
        action:      [throttle 0..1, rudder -1..1]  ->  cmd_fn -> JSON command
        reward:      -(speed - target)^2 - 4 heading_err^2 - 0.01 rudder^2
        truncated after episode_s; terminated never (no crash model here)
    twin_screw_cmd(thrusters, rpm_max, beta_max_deg)   action -> DTMB-type command
    single_propeller_cmd(max_rpm, max_rudder)          the original toy mapping
    surface_xdyn_param(port, thrusters)                <lotus_param> for CREATE
    FakeLink()                 3-DOF toy boat, same interface, no ROS needed

Python dependencies inside NixOS come from the dev shell flake (rclpy,
lotusim_msgs, numpy, gymnasium from the same nixpkgs as LOTUSim):

    nix develop path:/mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup

Run the demo (simulation running in another terminal):

    bash /mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup/run_gym_demo.sh --seconds 120 --target-speed 3

Expected output: "vessel name: dtmb_hull_0", a first pose, then a line every
5 s with speed, yaw rate, heading error, throttle, rudder; the DTMB is a 142 m
ship so it takes a minute to reach a few m/s. Ctrl+C or the end deletes the vessel.

Test the env without LOTUSim (any machine, Windows included):

    python control_envs/lotusim_env.py        -> Gymnasium check_env + P controller on FakeLink

Writing your own controller: subclass nothing; call env.reset(), loop
env.step([throttle, rudder]). For RL use the same env with
stable-baselines3 (not in the dev shell yet; add python3Packages.stable-baselines3
to flake.nix or run the learner on the Windows side and talk to LOTUSim through
the mirrored network - see Open items).


6. Troubleshooting
------------------
No window with --gui:          install the Intel/AMD bridge as fallback:
                               nix profile add github:nix-community/nixGL#nixGLIntel
                               (NixOS-WSL with wsl.useWindowsDriver = true should not need it)
ROS nodes do not see each other: mirrored networking blocked by Windows Firewall
                               (allow vEthernet/WSL), or NixOS firewall (the snippet
                               disables it). FASTDDS_BUILTIN_TRANSPORTS=UDPv4 is set
                               by the dev shell and by the lotusim wrapper.
Nix compiles for an hour:      the trusted keys are missing; check that
                               nixos-rebuild switch succeeded and /etc/nix/nix.conf
                               lists the two substituters.
"No vessel positions yet":     the vessel was not spawned, or xdyn is not running on
                               the port given in <lotus_param>; start xdyn first.
Vessel does not move:          command keys must match the xdyn YAML's controlled
                               force names exactly ("PSPropRudd(rpm)"); rpm is in
                               rad/s for the DTMB (30 = cruise).
WSL out of memory:             raise memory= in .wslconfig; wsl --shutdown; reopen.
First `wsl -d NixOS` is slow:  normal, it unpacks the image.


7. Status and fixes found on first execution (2026-10-21)
--------------------------------------------------------
Executed on this machine on 2026-10-21 (Windows 11, WSL 3.0.3, NixOS-WSL
2605.7.2): steps 1.2, 1.4, 2 and 3 all work, the headless demo drives the
DTMB hull through the Gymnasium env (spawn -> poses -> commands -> delete).
Four things had to be fixed on the way; they are now in the kit:
  a) A real RESTART is needed after enabling the Windows features. With
     "Fast Startup" on, shutting down and switching on again is NOT a
     restart (the kernel is hibernated and resumed); check with
         (Get-CimInstance Win32_OperatingSystem).LastBootUpTime
     and use Start -> Power -> Restart, or  shutdown /r /t 0.
  b) nixos-rebuild switch ended with "the following units failed:
     wsl-mnt-guard.service" (exit 4): WSL 3 generates that unit with
     ExecStart=/bin/true, which NixOS does not have. configuration.nix.snippet
     now adds a tmpfiles rule that creates /bin/true; fix_wsl_true.sh patches
     an already-edited configuration.
  c) The lxdyn flake has no default package: install  github:naval-group/lxdyn#xdyn
     (binaries xdyn, xdyn-for-cs, xdyn-for-me). nixos_setup.sh does this now.
  d) gymnasium from nixpkgs drags in opencv, which is not in the caches and
     fails to build. flake.nix now takes numpy and rclpy from nix and installs
     gymnasium with pip into ~/.venv-lotusim (created on first nix develop).
  e) ROS 2 discovery between the simulator and the Python client did not work
     with the defaults (no topics seen). Both sides now export
     ROS_LOCALHOST_ONLY=1, ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST and
     FASTDDS_BUILTIN_TRANSPORTS=UDPv4 (run_sim.sh and the flake's shellHook).
     Anything you start by hand must export the same three, or it will not
     see /lotusim/poses. ros_probe.py prints what a node can see;
     ros_diag.sh compares the settings.
  f) The Gazebo window: WSLg (DISPLAY=:0) and the NVIDIA bridge (/dev/dxg,
     /usr/lib/wsl/lib) are present; see section 8 for the recorded demo.
  g) Several simulator instances ended up running at once (pkill -f patterns
     do not match the gz processes, which are named .gz-wrapped and re-title
     their command line). Symptoms: "more than one action server for
     /lotusim/mas_cmd", commands answered with "No known entity", a vessel
     that does not move. ALWAYS stop with  sim_reset.sh  (kills by PID) before
     starting a new simulation.
  h) gz-transport (the simulator's own pub/sub, used between the server and
     the Gazebo window) needs UDP multicast; WSL has no multicast route
     ("Exception sending a multicast message: Network is unreachable").
     sim_reset.sh adds 224.0.0.0/4 on lo and sets lo multicast on; run_sim.sh
     exports GZ_IP=127.0.0.1 and GZ_RELAY=127.0.0.1.
  i) THE GAZEBO WINDOW DOES NOT SHOW THE SCENE on this machine (2026-10-21):
     the window opens (toolbar, play/pause, real-time factor ticking, the
     world control service works), but the 3-D viewport stays grey and the
     entity tree stays empty, in both modes (lotusim run --gui, and a
     separate client lotusim -g against a headless server), on Wayland and on
     X11 (QT_QPA_PLATFORM=xcb), with the only OpenGL available here being
     Mesa llvmpipe (software): the NVIDIA bridge /dev/dxg exists but Mesa
     reports "MESA-LOADER: failed to retrieve device information", so the
     d3d12 driver is not usable (gl_check.sh prints this). The debug log
     (lotusim run --gui --debug) shows ogre2 and MinimalScene initialised and
     no error. Not resolved; gz_shapes_test.sh reproduces it with Gazebo's own
     shapes.sdf, so it is the Gazebo-under-WSLg path, not LOTUSim. On a native
     Linux machine with a GPU none of this applies. For a picture of the run
     use the web UI (lotusim-ui, http://localhost:8080, Leaflet map) or the
     track video (control_envs/lotusim_track_video.py) instead.
Still open:
  - Only the DTMB hull has controllable xdyn forces among the shipped surface
    models; our 5.4 m planing boat would need its own xdyn YAML (displacement-
    type hydrodynamics only: xdyn has no planing lift), so LOTUSim is for
    demonstration and interface work, not for the planing physics (see
    learn/meta/LOTUSIM_GAP_2026-10-05.md).
  - stable-baselines3 is not in the dev shell; pip install it into
    ~/.venv-lotusim the same way as gymnasium, or train on the Windows side.
  - The simulation ran at about 0.8-1.0 x real time headless on this machine.
  - Command units: the JSON command values reach xdyn in SI whatever the
    YAML's commands block says -- beta in RADIANS (not degrees), rpm in rad/s.
    twin_screw_cmd() converts its beta_max_deg to radians since 2026-10-21;
    earlier runs sent 35 (radians!) and the ship turned erratically.
    beta > 0 turns the ship to port (+yaw); about 1-1.5 deg/s at 0.35 rad
    (20 deg) and 3.4 m/s on the DTMB, i.e. a minute per 90-degree turn. At
    0.61 rad (35 deg) the ship did not turn at all (rudder stall in the
    model), so twin_screw_cmd defaults to 20 deg.


8. Demo: a vessel following waypoints, recorded as a video (added 2026-10-21)
-----------------------------------------------------------------------------
Controller demo (two loops, a few lines of Python; see the docstring of
control_envs/lotusim_waypoint_demo.py):
    speed loop      PI on the speed error -> throttle
    heading loop    P on the heading error + yaw-rate damping -> rudder
    guidance        heading reference = bearing to the next waypoint
                    (square of --side metres, or a figure of eight)

Test it anywhere, without LOTUSim (toy boat):
    python control_envs/lotusim_waypoint_demo.py --fake --course eight

In NixOS-WSL with the simulation running (terminal 1):
    bash /mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup/run_sim.sh --gui
and in terminal 2:
    bash /mnt/c/Users/Administrator/Documents/usv-rl-mpc/control_envs/lotusim_setup/run_gym_demo.sh \
        --script waypoint --course square --side 800 --accept 120 --target-speed 5 --seconds 1500
The DTMB hull is a 142 m ship (the only shipped surface model with
controllable forces). Measured 2026-10-21: it holds about 4 m/s at rpm 80 x
0.75, and its steady turning circle with 20 degrees of rudder plus full
differential thrust is about 570 m in radius (yaw rate 0.4 deg/s after a
1.5 deg/s transient). So: legs of 800 m or more, --accept 120, and the demo
also counts a waypoint as passed once the ship is abeam of it. A lap of the
800 m square takes about 20 minutes of simulated time (the simulation runs
at 0.8-1.0 x real time here). The track is saved as JSON (--log).

Make the video from the saved track (works on any machine, no Gazebo window):
    python control_envs/lotusim_track_video.py control_envs/_out/lotusim_track_square.json --speed 12
    -> control_envs/_out/lotusim_track_square.mp4 (chart of track + waypoints +
       ship to scale, with speed / heading error / rudder against time).
    Example produced 2026-10-21: control_envs/_out/lotusim_square.mp4 (97 s for a
    1167 s lap of the 800 m square).

Recording the Gazebo window instead (only where the window renders -- it does
NOT on this WSL machine, see section 7 i):
  a) Gazebo's own recorder: in the Gazebo window open the plugin menu (the
     three dots, top right) -> "Video Recorder"; it writes an .mp4 next to the
     Gazebo working directory, same frame rate as the window. Best quality.
  b) Windows screen recording of the Gazebo window (it is an ordinary Windows
     window under WSLg): Win+G (Game Bar) -> Capture -> Record; or OBS.
     Simplest; records exactly what you see, including the follow camera.
  c) Headless: run without --gui, keep the track JSON, and make the video in
     Blender from the poses (app/export.py exports a run for Blender; the
     JSON here has x, y, yaw at the control step).
Camera: in Gazebo right-click the vessel -> "Follow" to keep it in view;
"Move To" jumps there. The web UI (lotusim-ui, http://localhost:8080) also
shows the vessel on a map, which can be recorded the same way.
